# AI 内阁会议五｜main 合并、预览与后续迭代策略

> **议题**：用户想把网站放到 `main` 看正式部署效果，但担心合并/PR 后 Arena 远程协作能力中断，后续无法继续修改。是否用 `HANDOFF.md` 解决？
>
> **会议时间**：2026-08-02。

## 1. 实际状态证据

- 当前 `main` 与工作分支均指向 `ae0ad6d`；
- 当前工作区包含本轮网页、文档、预览和交付物的大量未提交改动；
- 这意味着“先做 main 部署”不是首要风险，**先保护未提交成果**才是首要风险；
- Cloudflare Pages API Token 不在当前环境；GitHub Pages 也未启用且当前 GitHub 集成没有仓库管理权限；
- 本地 `npm run dev` / `npm run preview` 是现在唯一可验证的完整预览路径。

## 2. 角色意见

### 架构工程师

- PR 和分支是版本管理机制；正常情况下，合并 main 不会自动删除工作分支或禁止向该分支继续 push。
- 但 Arena 是否结束会话、收回远程能力是平台行为，Git 无法控制，也不能保证。
- 先提交固定分支快照，后续才有可恢复基础。

### 发布工程师

- 不能为了看生产 URL 跳过素材、链接、真机和事实核验。
- 生产部署应该是上线检查完成后的结果，而不是调试工具。
- 如果一定要先合并 main，至少采用 Draft PR → 本地验收 → 正式合并的顺序。

### 风险工程师（反对派）

- 未提交工作区是最高风险：平台刷新、重置、误操作都可能造成改动丢失。
- `HANDOFF.md` 只能解释如何恢复，不能恢复未提交、未推送的代码。
- 因此 `HANDOFF.md` 必须和分支 commit 同时存在，不能只写文档不提交。

### 产品工程师

- 用户真正需要的是“看最新版效果”，而非一定要把它提前变成 main。
- 本地预览满足视觉和交互验收；生产 URL 只在准备上线时使用。

### 交接工程师

- `HANDOFF.md` 是必要的：记录分支、构建命令、关键文件、待确认项、不可擅自修改事实、部署限制和恢复流程。
- 它不是权限系统，不应被理解为“合并后一定还能远程工作”的保证。

## 3. 裁决

1. **立即做**：将所有当前成果提交并推送到固定 `arena/019fc032-repo` 分支，并提交 `HANDOFF.md`。
2. **暂不做**：不创建 PR、不合并 main，直到用户在本地预览验收最新页面。
3. **若需要 PR**：创建 Draft PR 是安全的，它不合并；未来提交自动更新它。
4. **若必须看 main 的正式部署**：应当在本地验收、完成上线检查后再合并；这是一项发布决策，不是预览决策。
5. **平台风险说明**：任何 `HANDOFF.md` 都不能保证 Arena 的会话/远程权限；它能确保下一位 agent 有足够信息在新会话继续工作。
