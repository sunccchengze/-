# 有 Deadline 型任务的执行指导

## 适用场景

用户明确给出完成截止时间，并要求在截止前持续、独立工作，例如：

- “从现在开始做到 22:50，期间不要停工”；
- “截止前不要汇报、不要提交”；
- “不需要我逐步确认，先自行完成可独立完成的部分”。

## 第一原则

把截止时间视为**连续工作窗口**，不是“做一小步就回复一次”的聊天任务。

在用户明确要求截止前不汇报或不提交时：

- 不发送“继续中”“正在做”“请回复”“我会继续”等阶段性占位消息；
- 不把一次扫描、一次构建、一次小改动当成应汇报的节点；
- 不创建提交、不推送，除非用户明确要求立即提交/推送；
- 不把“无法等待”当成提前结束独立工作窗口的理由。

## 启动流程

1. **读取时间**：先获取用户指定时区的当前时间，明确剩余工作时长。
2. **识别约束**：记录“禁止汇报”“禁止提交”“截止时间”“必须做的事”“不可触碰的事实”。
3. **分离任务**：
   - 可独立执行：资源存在性、类型、构建、占位语、锚点、图片/视频解码、公开文案、可访问性、源代码交互检查、视觉源代码审查；
   - 必须用户确认：事实是否成立、活动是否真实、正式链接、用户偏好的视觉方向。
4. **排定批次**：优先处理会造成公开错误、构建失败、缺图、占位语、虚构内容、失效交互的问题，再处理视觉与维护性。

## 连续工作规则

### 在截止前

- 连续执行多个独立检查批次；
- 每个批次记录实际结果，不将推断写成验证；
- 发现可独立修复的代码问题，修复到工作区，但按用户约束暂不提交；
- 发现需要确认的问题，记录在审查清单，不用闲聊打断工作；
- 不自行宣布“完成”“交付”“收工”。

### 在截止时

一次性完成：

1. 最终时间确认；
2. 运行类型检查、资源检查、构建检查；
3. 汇总真正修复项、验证项、未验证项、待确认项；
4. 仅在用户允许时统一 commit / push；
5. 汇报必须区分“已验证”与“尚待人工/设备验证”。

## 招新网站专项检查清单

1. **公开内容**：无“待替换、预留、整理中、TODO、测试、秋招、秋季招新、刷工时、工时可认证、保证录取、调剂”等不应出现的文字。
2. **事实边界**：官方项目/奖项全称不得自行改写；未确认事实不得补写。
3. **资源**：每个配置图片、二维码、视频、荣誉证明路径存在且可由开发服务器返回；图片可解码。
4. **交互**：内部锚点均有对应 DOM id；按钮有明确类型；正常页面不展示内部比较器。
5. **工程**：`typecheck`、资源校验、生产构建均通过；无无引用图片或过期导入。
6. **最终人工项**：WPS 表单、外部公众号链接、手机真机、微信/QQ 内置浏览器、二维码扫码，必须明确标注为人工验证，不能伪称已验证。

## 反例

以下做法均不合格：

- 做一轮检查就发“继续审查中”；
- 用户要求截止前不提交，仍然分多次 commit / push；
- 用“我会继续”代替实际连续执行；
- 因为等待用户确认一个视觉问题，就停止所有其他可独立进行的检查；
- 把外部网络不可达、真机未测、事实未确认写成“已验证”。

## 结论

Deadline 型任务要求的是在一个时间窗口内持续推进的执行力。阶段性沟通、阶段性提交和提前收工，都会破坏用户需要的自动化工作体验。
